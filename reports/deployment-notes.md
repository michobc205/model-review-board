## 6. Reflection

### Why a local SQLite file helps in development

SQLite needs no server and no setup: the database is one file next to the app, which is fast to create, easy to reset by deleting it, and works offline. Tests can use a fresh file every time. Because the app uses Flask-SQLAlchemy, the same code runs on SQLite locally and on PostgreSQL after the deployment. Only the `DATABASE_URL` changes.

### Why it is unsuitable for a free Render web service

A free Render web service has an **ephemeral filesystem**: changes to local files, including a local SQLite database, are lost every time the service redeploys, restarts or spins down, and a free service spins down after 15 minutes without traffic. Free services cannot attach a persistent disk. A SQLite file would therefore lose every review soon after it was saved. A single file also cannot be shared safely by several instances of the service. A managed PostgreSQL database lives outside the web service, so the reviews survive restarts and redeploys, and the service finds it through `DATABASE_URL`.

### One change before sensitive production data

**Authentication and access control.** Today anyone who knows the address can read, change and delete every review. Before the app holds sensitive review data, reviewers must log in, and the app must check what each person is allowed to see and do. After that, the next steps would be protection of the forms against forged requests (CSRF), HTTPS only, a paid database with backups, and an audit log of who changed which decision.
