# Model Review Board

A small web app where an ML team reviews model predictions before another department uses them. Reviews are stored in a relational database, so every reviewer sees the same decisions and notes, and notes survive handovers.

The first version is modest on purpose: server-rendered HTML, a few routes, one database table, and one hosted deployment. The task is in [`project-for-today.md`](project-for-today.md).

## What you can do

1. Open the **dashboard**: all reviews and the number of reviews per status (pending, approved, rejected).
2. **Create** a review with a case reference, a prediction, a confidence between 0 and 1, and a short input summary.
3. **Change the decision** to approved or rejected and add notes.
4. Open the app in **another browser session** and read the saved decision.
5. **Delete** a review only through an explicit form action (a confirmation page, then a POST request).

Wrong input is rejected with a message next to each field. `/health` answers 200 if the database works and 503 if it cannot be reached.

## Technology

Flask routes with Jinja templates, Flask-SQLAlchemy with one `Review` model, SQLite locally and PostgreSQL after the deployment (the app reads `DATABASE_URL`), gunicorn on Render, pytest for the tests. No Dockerfile.

## Run it locally (no cloud account needed)

```bash
uv venv --python 3.13
uv pip install -r requirements-dev.txt
cp .env.example .env                       # local settings, ignored by Git
.venv/Scripts/flask --app review_board init-db     # create the table
.venv/Scripts/flask --app review_board seed-db     # optional: three sample reviews
.venv/Scripts/flask --app review_board run --debug
```

Then open `http://127.0.0.1:5000`. On macOS or Linux, use `.venv/bin/flask` instead of `.venv/Scripts/flask`.

## Run the tests

```bash
.venv/Scripts/python -m pytest -q
```

99 tests cover the model, the settings, the commands, the dashboard, the validation, create, edit, delete, the health check, and the deployment files (`render.yaml`, `.gitignore`, `.env.example`).

## Configuration

| Variable | Meaning | Where it comes from |
|---|---|---|
| `DATABASE_URL` | The database address. Default: a SQLite file in the `instance` folder. | `.env` locally, the managed database on Render |
| `SECRET_KEY` | Signs the session cookie (used for the messages after a form) | `.env` locally, generated by Render |

`.env.example` has placeholders only. Real secrets, copied database URLs and local database files are never committed (`.gitignore` covers `.env`, `*.db` and `*.sqlite`).

## Deployment

`render.yaml` describes the web service and the database, and connects them with a managed `DATABASE_URL` (no copied credential). Both plans are `free` and written down explicitly. Free web services spin down after 15 minutes without traffic and have an ephemeral filesystem, which is why the data lives in PostgreSQL and not in a file.

**Live app (free plan, test data only):** <https://model-review-board-pfo7.onrender.com>

- **Available until about 24 November 2026**, when it is planned to be removed. The free database expires on **26 November 2026** at the latest, so **the link does not work after that date**. The evidence below stays in this repository.
- The first load can take about a minute, because the free service goes to sleep after 15 minutes without traffic.
- The app has no login. Please use made-up data only.

The evidence (a review that survives a redeploy, the health check, the log lines, the slow first load, and the cost checks) is in [`reports/deployment-notes.md`](reports/deployment-notes.md), with pictures in `reports/evidence/`.
