## 4. One observed limitation

**A free web service spins down after 15 minutes without traffic, and the next request is slow.**

- The last browser request was at 19:21:21 in the log. Exactly 15 minutes later, at about 19:36, the log shows `Shutting down: Master`: the service went to sleep. Render's own `/health` checks did not keep it awake.
- The next page load, at about 20:40 local time, took **44.49 seconds** (measured with a stopwatch) before the dashboard appeared. Before that, while the service was awake, the page appeared in under 10 seconds.
- Render's own banner says the same: a free instance spins down with inactivity, "which can delay requests by 50 seconds or more".

The data was not lost: the review was still there after the slow start.

## 6. Reflection

### Why a local SQLite file helps in development

SQLite needs no server and no setup: the database is one file next to the app, which is fast to create, easy to reset by deleting it, and works offline. Tests can use a fresh file every time. Because the app uses Flask-SQLAlchemy, the same code runs on SQLite locally and on PostgreSQL after the deployment. Only the `DATABASE_URL` changes.

### Why it is unsuitable for a free Render web service

A free Render web service has an **ephemeral filesystem**: changes to local files, including a local SQLite database, are lost every time the service redeploys, restarts or spins down, and a free service spins down after 15 minutes without traffic, as section 4 shows. Free services cannot attach a persistent disk. A SQLite file would therefore lose every review soon after it was saved. A single file also cannot be shared safely by several instances of the service. A managed PostgreSQL database lives outside the web service, so the reviews survive restarts and redeploys, as section 3 shows, and the service finds it through `DATABASE_URL`.

### One change before sensitive production data

**Authentication and access control.** Today anyone who knows the address can read, change and delete every review. Before the app holds sensitive review data, reviewers must log in, and the app must check what each person is allowed to see and do. After that, the next steps would be protection of the forms against forged requests (CSRF), HTTPS only, a paid database with backups and no 30-day expiry, and an audit log of who changed which decision.
